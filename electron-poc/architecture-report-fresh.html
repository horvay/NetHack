Architecture readout

The Electron POC has already established useful seams: child process ownership is in main/game-process.js, security hardening is in main/electron-security.js, replay automation is in main/replay-runner.js, and several renderer rules have been extracted into frozen CommonJS/browser-global shared modules. The strongest current risk is that renderer.js remains the high-change module where several independent concepts meet: shim event interpretation, NetHack prompt/menu state, tile terrain presentation, recording, keyboard routing, test adapters, and DOM rendering.

The most valuable next work is not to create more tiny pass-through modules. It is to deepen a few modules so the renderer becomes a DOM adapter over tested NetHack view state.

Deepening opportunities

1. Deepen a shim game view-state module

Files/modules: src/renderer.js, src/shared/shim-protocol.js, scripts/fixture-view-test.js, test/fixtures/*.jsonl, shim-bridge/nh-shim-bridge.c.

Problem: the renderer directly consumes shim events and mutates many state stores: map cells, cursor, status fields, menus, prompts, text windows, cached inventory choices, and message history. The fixture script independently re-implements a smaller version of the same event interpretation. That gives tests independence, but it also splits behaviour across two implementations and makes the renderer the only place where the real event ordering invariants are visible.

Solution: create a deep shared module that accepts normalized shim events and returns a NetHack view-state snapshot plus high-level effects such as “show prompt”, “open document window”, “mark cells dirty”, or “record milestone”. Keep DOM writes and Electron calls in the renderer adapter. The C shim remains an adapter that emits raw events; shim-protocol.js becomes the event normalization seam feeding the view-state module.

Benefits: locality improves because event ordering, menu-window lookup, prompt cancellation, and status semantics live in one implementation. Leverage improves because fixture tests, browser automation, replay, and the renderer can exercise the same interface. The deletion test suggests this module would earn its keep: deleting it would force event-state complexity back into every caller and test.

2. Turn prompt/menu rules into an interaction model module

Files/modules: src/renderer.js, src/shared/prompt-rules.js, src/shared/command-gateway.js, scripts/fixture-view-test.js, scripts/gui-input-workflow-test.js.

Problem: prompt-rules.js is useful but still shallow: it exposes regex predicates while the renderer owns the harder implementation — inventory-cache use, action prompt titles, item-class rows, direction-helper suppression, menu selection feedback, passive ground-menu suppression, and cancellation behaviour. The same concepts appear in fixture checks and UI automation scripts.

Solution: deepen this into a prompt/menu interaction model module. Given active NetHack prompt/menu state and cached inventory choices, it should produce a plain interaction description: title, prompt copy, options, text-entry mode, selection semantics, and cancellation behaviour. The renderer adapter renders that description into dialogs/buttons.

Benefits: locality improves for the highest-risk UX rules: NetHack prompt interpretation. Leverage improves because tests can assert interaction descriptions without launching Electron for every case, while browser tests can focus on DOM fidelity. This also narrows the renderer interface to “render this interaction model” instead of “know NetHack prompt grammar”.

3. Move tile/cell presentation from renderer fallback logic into a map presentation module

Files/modules: src/renderer.js, src/shared/tile-assets.js, scripts/map-tooltip-test.js, assets/tiles/manifest.json, assets/tiles/tile-map.json.

Problem: tile-assets.js resolves asset ids and overlay/base rules, but the renderer still owns terrain CSS classes, wall/door neighborhood dependencies, tooltip significance rules, fallback glyph behaviour, and ARIA labeling. That spreads map presentation knowledge across a shared module and DOM code.

Solution: deepen a map presentation module that converts a normalized cell plus neighborhood context into a cell view model: terrain classes, tile id, base tile id, fallback glyph, tooltip model, and accessibility label. The renderer should only apply that model to an element.

Benefits: locality improves for tile QA fixes and asset semantics. Leverage improves because map tooltip tests, fixture rendering checks, and visual replay assertions can exercise the same presentation interface without duplicating renderer details.

4. Make shim protocol events a versioned contract, not only a wrapper

Files/modules: shim-bridge/nh-shim-bridge.c, src/shared/shim-protocol.js, test/fixtures/*.jsonl, scripts/bridge-input-behavior-test.js, scripts/fixture-view-test.js.

Problem: the C shim emits ad hoc JSON fields and shim-protocol.js mostly wraps them with kind, known, and raw payload preservation. The interface callers must know includes field presence, numeric ranges, event ordering, callback-specific semantics, and when bridge events answer prompts. Those invariants are mostly implicit.

Solution: define a versioned shim event contract in JS with per-event normalization/validation for high-value events. Keep raw events for diagnostics, but give callers a stable normalized payload. Fixtures can then be validated against the contract before view-state tests run.

Benefits: locality improves when C shim fields change. Leverage improves because both renderer and tests can rely on one normalized interface. This is a real seam because there are already multiple adapters/callers: C shim output, fixture replay, renderer consumption, and behavior tests.

5. Replace preload validator duplication with an explicit generation/embedding seam

Files/modules: src/preload.js, src/shared/preload-contract.js, test/shared/architecture-modules-test.js.

Problem: preload.js duplicates validator logic from preload-contract.js because sandboxed preloads cannot require local files. The current comment/documentation makes the reason clear, but the interface can drift: tests import the shared copy while production executes the inline copy.

Solution: add a small build/check module that treats preload-contract.js as the source and embeds or verifies the preload copy. If no build step is desired, add a test that compares the two validator bodies or generated hashes.

Benefits: locality improves for IPC validation. Leverage improves because the existing Node-testable interface would become the actual production source rather than a parallel copy.

6. Deepen the Electron/CDP test harness before adding more browser workflow scripts

Files/modules: src/shared/test-harness.js, scripts/gui-input-workflow-test.js, scripts/map-tooltip-test.js, scripts/direction-helper-layout-test.js, scripts/log-panel-behavior-test.js, scripts/prompt-spam-state-test.js.

Problem: test-harness.js is currently shallow compared with the repeated implementation in browser workflow scripts: spawn Electron, wait for CDP, connect WebSocket, evaluate JS, capture screenshots, cleanup. The repeated code is understandable for a POC, but every new visual workflow inherits the same timeout and cleanup surface.

Solution: deepen test-harness.js into the one module that owns Electron/CDP workflow setup, evaluation, screenshot capture, and cleanup. Scripts should provide scenario steps and assertions, not transport mechanics.

Benefits: locality improves for flaky-test fixes and port/env handling. Leverage improves because each new scenario gets a smaller interface and fewer ways to leak processes or diverge on timeout behaviour.
