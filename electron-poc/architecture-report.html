NetHack Electron Architecture Improvement Report

Scope: only the Electron app on top of NetHack. NetHack core/C architecture was not audited except for the Electron shim seam.

Executive summary

The Electron app is a productive proof of concept with unusually good fixture/replay coverage for its age. The main architectural friction is that the renderer is one very large shallow module: UI widgets, game state, event interpretation, input safety, settings, tile selection, logging, prompt handling, recording, and browser-preview behavior all share global mutable state in electron-poc/src/renderer.js (2,018 lines). That gives quick iteration but weak locality: a change to item prompts can affect menus, recording, key routing, log panels, and automation hooks.

The strongest deepening opportunities are to create a small set of durable modules around the real domain seams already present: shim event stream, dungeon view model, prompt/menu interaction state, command/input gateway, asset resolver, recording/replay harness, and log/message store. The goal is not to add layers; it is to put more behavior behind smaller interfaces so tests and future UI work cross the same seams as the app.

Deepening opportunities by area

A. Electron process, preload, and shim seams

1. Create a deep Game Process module in the main process P0 medium refactor

Problem. Child process lifecycle, seed/options normalization, shim startup, TTY startup, stdout/stderr routing, duplicate-key suppression, and recording save path construction are all in src/main.js. The deletion test says this code is earning its keep, but the current interface is not explicit; callers indirectly depend on globals child, childMode, childSeq, childStopping, and lastShimKey.

Evidence. src/main.js:18-23 global process state; 148-174 attachChild/stopChild; 194-227 TTY and shim launch handlers; 238-263 input routes.

Recommended approach. Move lifecycle behavior behind one Game Process module with a small interface: start TTY, start shim, stop, status, write input, and subscribe to events. Keep Electron IPC as a thin adapter.

Implementation steps

  • Extract pure normalization helpers first with tests.
  • Introduce a game-process module owning child state.
  • Make IPC handlers delegate only to that module.
  • Represent child output as typed app events before forwarding to renderer.

Risks/tradeoffs

  • Refactor touches launch behavior used by tests.
  • Over-abstracting before a second adapter exists would be shallow; keep one module, not many.

Suggested tests. Unit tests for seed/options; integration tests for one-child-at-a-time, expected stop exit, shim stdout parse errors, non-shim input rejection, and duplicate key suppression.

2. Define and validate the preload Interface P0 quick win

Problem. The preload module exposes a powerful interface to the renderer without argument shape validation or unsubscribe handles for listeners. This is a shallow pass-through: its interface is almost identical to raw IPC.

Evidence. src/preload.js:3-16 exposes startShimBridge, shimInput, saveRecording, and event listeners directly.

Recommended approach. Deepen the preload module: validate inputs, freeze payloads where useful, return unsubscribe functions for event subscriptions, and document the allowed message schema. Keep the Interface tiny and stable for renderer tests.

Implementation steps

  • Add small validators for player spec, seed, options, recording, keycode payload.
  • Wrap ipcRenderer.on with listener removal.
  • Expose a versioned netHackPOC contract object.

Risks/tradeoffs

  • Validation can reject currently tolerated loose calls from tests; migrate tests simultaneously.
  • Do not duplicate all main-process validation; preload should reject gross shape errors only.

Suggested tests. Preload contract tests in a BrowserWindow: invalid payloads do not reach IPC; event listener unsubscribe works; valid keycode and start options pass unchanged.

3. Version the shim event protocol at the Electron seam P0 larger improvement

Problem. Renderer logic branches directly on string event names such as shim_print_glyph, bridge_direction_prompt, and shim_status_update. The C shim and renderer are tightly coupled through an implicit, unversioned Interface.

Evidence. shim-bridge/nh-shim-bridge.c:114-121 event emission helpers; 423-677 callback emits many event shapes; renderer.js:1385-1516 handles these names directly.

Recommended approach. Treat the newline-delimited JSON stream as a versioned protocol module. Add a schema/version field or main-process normalization adapter that maps shim events into stable app events consumed by the renderer.

Implementation steps

  • Inventory current event names and payload fields from fixtures.
  • Create a shim-event-normalizer in JS that accepts raw shim events and returns typed app events.
  • Emit protocol metadata from the bridge or attach it in main process.
  • Gradually make renderer consume app events, not raw shim callbacks.

Risks/tradeoffs

  • A second event vocabulary can cause confusion; name it carefully and keep raw logging available.
  • C changes are optional initially; start in Electron to avoid core/shim churn.

Suggested tests. Fixture-driven normalizer tests for every current event name; golden snapshots for accepted app events; compatibility tests against existing test/fixtures/*.jsonl.

4. Split automation/replay orchestration out of normal app startup P1 medium refactor

Problem. Visual replay is embedded into createWindow and calls renderer globals via executeJavaScript. This gives useful leverage for tests but couples app startup, test timing, screenshot capture, and renderer internals.

Evidence. src/main.js:35-41 triggers visual replay after load; 50-110 captures pages and drives window.__nethackAutomation; renderer.js:1934-1963 exposes automation hooks.

Recommended approach. Create a Replay Runner module whose adapter is selected by environment. Main process should only detect replay mode and delegate. The runner's interface should use app-level commands, not ad hoc JavaScript strings.

Implementation steps

  • Move env parsing and screenshot cadence into a replay module.
  • Route replay commands through the same input gateway used by UI.
  • Define a stable automation state shape shared with tests.

Risks/tradeoffs

  • Replay scripts may need updates.
  • More ceremony for one mode, but better locality for timing fixes.

Suggested tests. Unit tests for replay config defaults; end-to-end visual replay smoke; failure test for missing/unsupported recording schema.

B. Renderer state and data flow

5. Replace the monolithic renderer with a small set of deep state modules P0 larger refactor

Problem. renderer.js mixes domain state, DOM rendering, input routing, prompt heuristics, asset lookup, settings, recording, and test hooks. This is the main locality problem: understanding one change requires scanning most of the file.

Evidence. renderer.js:11-104 DOM/global state declarations; 177-407 map and asset functions; 564-711 messages/settings/context prompts; 797-1378 dialogs/menus; 1385-1516 event reducer; 1712-1932 input routing.

Recommended approach. Introduce deep modules with interfaces based on app concepts: Dungeon View Model, Prompt State, Menu State, Message Log, Status HUD, Command Gateway, Asset Resolver, Recorder, and Renderer Shell. The renderer shell wires modules to DOM.

Implementation steps

  • Start with pure modules: asset resolver, prompt classifier, menu classifier, message log.
  • Move global state into explicit state objects.
  • Make processShimGameEvent call reducers that return render intents.
  • Keep DOM updates in existing file until models are stable, then extract view adapters.

Risks/tradeoffs

  • Big-bang extraction could break many UI paths; migrate one module per PR.
  • Too many tiny modules would be shallow. Each extracted module must pass the deletion test.

Suggested tests. Pure reducer tests using fixture events; renderer smoke tests verifying DOM outputs did not change; mutation-style tests for prompt/menu interactions after event sequences.

6. Make shim event processing a reducer, not a DOM dispatcher P1 medium refactor

Problem. processShimGameEvent both interprets events and directly mutates UI state/DOM scheduling. This makes bugs hard to localize and forces tests to inspect browser globals rather than a stable state interface.

Evidence. renderer.js:1385-1516 updates map cells, messages, menus, prompts, status, windows, recordings, and render scheduling in one function.

Recommended approach. Create a Game State reducer module. It consumes normalized app events and returns state plus render effects. DOM adapters subscribe to changed slices.

Implementation steps

  • Define state slices for map, cursor, windows, menu, prompt, status, logs.
  • Convert one event family at a time.
  • Represent effects such as openDocumentWindow, flushMapRenderNow, and recordMilestone explicitly.

Risks/tradeoffs

  • Effect modeling can become over-engineered; keep effects as simple tagged objects.
  • Initial duplication with existing globals during migration.

Suggested tests. Given event sequences, assert final game state and effects; re-use fixture JSONL files as reducer tests independent of Electron.

7. Build a single Command Gateway for all player input P0 medium refactor

Problem. Input safety is spread across keyboard events, quick actions, dialogs, direction helper, contextual prompts, automation, recording, and main-process duplicate filtering. The same conceptual command can travel through multiple paths.

Evidence. renderer.js:1712-1776 key support, de-duplication, text sending, recording; 1779-1932 quick actions, modal key routing, document keydown; main.js:250-257 second duplicate suppression path.

Recommended approach. Create a Command Gateway module that accepts intent objects (key, text, menu selection, cancel, contextual action) and is the only module that writes to shimInput. UI and automation become adapters.

Implementation steps

  • Define accepted command intents and validation rules.
  • Move isSupportedPlayableKey, duplicate suppression, recording calls, and rememberWorldKey into the gateway.
  • Make quick actions/dialogs/automation call the gateway.
  • Keep main-process validation as a last safety net.

Risks/tradeoffs

  • Input bugs are user-visible; migrate with exhaustive input-safety tests.
  • Need to decide which duplicate suppression belongs in renderer vs main; document the invariant.

Suggested tests. Existing test:input-safety, plus unit cases for repeated keys, Ctrl-D, Escape, text entries, modal focus, automation keycode, and recording source attribution.

8. Deepen the prompt/menu interaction module P1 medium refactor

Problem. Prompt and menu behavior is feature-rich but embedded in many functions with shared globals activePrompt, currentMenu, cachedInventoryChoices, and activeContextualPrompt. Heuristics for questions, inventory actions, item classes, menus, and direction prompts are interleaved with DOM dialog rendering.

Evidence. renderer.js:949-1183 prompt classification; 1184-1378 menu classification/rendering; 1385-1479 event handling updates these states.

Recommended approach. Create an Interaction State module that converts prompt/menu events into a presentation model: kind, title, prompt copy, option rows, text-entry mode, selected keys, and command intents. Dialog DOM becomes an adapter for that model.

Implementation steps

  • Extract prompt/menu classifiers into pure functions.
  • Represent inventory rows and object-class rows as typed option objects.
  • Move selection expression parsing into the module.
  • Render the same model in the existing dialog.

Risks/tradeoffs

  • NetHack prompt text is varied; keep raw query and choices available for unknown prompts.
  • Some heuristics may belong in fixtures rather than hard-coded regexes long term.

Suggested tests. Fixture tests for action inventory, item use prompts, drop menu, ground pickup, yes/no, line input, extended command, direction helper, and cancellation.

9. Make dungeon map rendering consume a view model P1 medium refactor

Problem. Map state, tile choice, terrain CSS classes, dirty-cell tracking, tooltip data, and DOM writes are tightly coupled. This reduces locality when changing tile composition or performance behavior.

Evidence. renderer.js:164-173 map state; 208-310 tile/terrain logic; 333-400 DOM cell application; 411-493 tooltip logic; 504-560 full/partial rendering.

Recommended approach. Create a Dungeon View Model module that maps game cells to render cells: glyph, tile id, base tile id, terrain classes, ARIA label, tooltip content. A DOM adapter only applies render cells.

Implementation steps

  • Extract normalizeCell, tile selection, terrain classes, and tooltip info into pure functions.
  • Return render-cell objects instead of mutating elements.
  • Keep dirty-cell scheduler but feed it render-cell diffs.

Risks/tradeoffs

  • Potential performance overhead if render-cell objects are allocated for all cells too often; benchmark with existing render performance script.
  • CSS-class compatibility must be preserved.

Suggested tests. Unit tests for representative cells; map tooltip tests; render performance budget tests; visual screenshots for doors, floors, overlay sprites, unknown glyph fallback.

10. Make status parsing a Status HUD module P2 quick win

Problem. NetHack status fields and rendering are directly embedded in the renderer. It is small enough today, but condition masks and field labels are domain rules that deserve a stable test surface.

Evidence. renderer.js:711-795 field names, value cleaning, condition mask decoding, HP class, status render.

Recommended approach. Extract a Status HUD module with input statusValues/statusLabels and output chips/raw status lines. This gives leverage for future status UI without touching event handling.

Implementation steps. Move constants and functions; return chip descriptors; DOM adapter renders descriptors.

Risks/tradeoffs. Low risk; avoid premature support for every NetHack status variant until fixtures reveal it.

Suggested tests. Condition mask decoding; HP danger/warning/healthy; gold value cleaning; empty HUD state.

11. Turn message history into a Message Log module P1 quick win

Problem. The log deduplicates, filters generic direction prompts, limits history, renders two panels, and triggers contextual prompts. These are multiple responsibilities hidden in appendMessage.

Evidence. renderer.js:564-581 rendering; 652-668 message normalization/dedup/history cap; 673-711 locked-door contextual prompt trigger.

Recommended approach. A Message Log module should own append/filter/dedup/history limit and emit optional observations such as “locked door mentioned.” Contextual action UI should subscribe to observations, not live inside append.

Implementation steps. Extract log state and append result; move locked-door detector to a contextual-actions module; keep DOM render unchanged initially.

Risks/tradeoffs. Too much event indirection can obscure simple log behavior; use simple return values.

Suggested tests. Duplicate suppression; history cap at 240; recent window at 80; generic direction prompt filtering; scroll position preservation using existing log-panel script.

C. Asset integration points

12. Create a Tile Asset Resolver module P1 medium refactor

Problem. Asset lookup combines manifest state, default maps, semantic aliases, glyph numbers, category rules, overlay/base composition, and browser-preview fallback inside renderer globals. Tests duplicate parts of this logic.

Evidence. renderer.js:85-122 manifest/map defaults; 123-145 semantic mapping; 221-249 URL/overlay/base tile logic; 1518-1554 manifest fetch and fallback; scripts/fixture-view-test.js:21-28 duplicated asset mapping.

Recommended approach. Define Tile Asset Resolver as a deep module: load manifest/map, resolve cell to asset/base/overlay information, expose diagnostics for missing mappings. Both renderer and fixture tooling use it.

Implementation steps

  • Extract resolver with no DOM dependency.
  • Move default tile map into a JSON or JS data file used by both app and tests.
  • Expose missing-asset telemetry for QA.
  • Keep browser-preview fallback as an adapter.

Risks/tradeoffs

  • Loading JSON in Electron/browser/test contexts needs a small adapter.
  • Resolver should not know CSS details beyond semantic output.

Suggested tests. Manifest coverage; glyph number mapping; semantic alias mapping; overlay/base composition; missing asset fallback; fixture-view tests using the shared resolver.

13. Add an asset manifest validation seam before renderer load P1 quick win

Problem. Renderer tolerates manifest fetch failure and falls back for browser preview, but production asset issues can silently degrade to ASCII or missing art. Asset QA exists, but runtime manifest validation is separate.

Evidence. renderer.js:1518-1554 catch block logs warning and supplies limited preview assets; package.json has test:manifest and visual QA scripts.

Recommended approach. Validate manifest shape, installed paths, duplicate ids, category consistency, and mapping references in one module invoked by tests and optionally in dev runtime.

Implementation steps. Add manifest schema checks; wire to test:manifest; surface validation summary in debug panel for development builds.

Risks/tradeoffs. Strict validation may fail while assets are actively being generated; support a warning mode for incomplete work.

Suggested tests. Duplicate id fixture; missing installedPath; tile-map reference to unknown asset; invalid workflow/category metadata.

D. Replay, fixtures, and test tooling

14. Share app modules with fixture tests instead of duplicating behavior P0 medium refactor

Problem. Fixture scripts re-implement asset resolution, prompt parsing, menu classification, and state updates. That catches regressions, but it can also become a parallel implementation that drifts from the app.

Evidence. scripts/fixture-view-test.js:21-76 duplicates slugifySemanticName, assetFor, promptSelectorSet, isInventoryActionPrompt, menuKind, and ground-menu suppression.

Recommended approach. After extracting pure modules, make fixture tests import the same modules and assert state/view-model outputs. Keep a small number of independent end-to-end tests for true black-box coverage.

Implementation steps

  • Convert pure modules to CommonJS first to match current package type.
  • Replace duplicated helpers in scripts with imports.
  • Keep JSONL fixture parsing in scripts.
  • Add golden app-state snapshots for fixture sequences.

Risks/tradeoffs

  • Shared code tests can miss bugs shared by app and tests. Preserve a few browser/CDP tests as independent verification.
  • Importing renderer-only modules into Node requires DOM-free design.

Suggested tests. Existing fixture suite should pass unchanged in assertions; add drift test that fixture helper imports are the source of truth.

15. Treat recordings as versioned artifacts with validation P1 quick win

Problem. Recording schema is named, but validation is minimal and split between renderer and main. Invalid or huge recordings could be saved, and visual replay only validates a few fields.

Evidence. renderer.js:1611-1655 creates/saves recording objects; main.js:230-236 writes whatever object it receives; main.js:63-68 replay schema checks are limited.

Recommended approach. Create a Recording module with versioned schema validation, normalization, max sizes, and migration hooks. Main process should validate before writing; replay should validate before playback.

Implementation steps. Define recording v1 schema; cap inputs/milestones/string lengths; sanitize character fields; add validator used by renderer, main, and replay scripts.

Risks/tradeoffs. Old recordings may fail strict validation; allow a migration or lenient read mode.

Suggested tests. Valid seeded recording; missing inputs; unsupported schema; oversized inputs; malformed keycodes; migration/no-op path for current fixtures.

16. Consolidate CDP/Electron test harness utilities P2 quick win

Problem. Many scripts launch Electron/CDP, wait for globals, evaluate snippets, and collect screenshots/metrics with similar code. Harness details are shallow modules repeated across tests.

Evidence. scripts/direction-helper-layout-test.js, log-panel-behavior-test.js, prompt-spam-state-test.js, map-tooltip-test.js, and render-performance-test.js all use CDP/evaluate patterns; grep shows repeated waits for window.__nethackPromptTest.

Recommended approach. Create scripts/lib/electron-harness.js as a deep test module: launch app, attach CDP, wait for automation object, evaluate, screenshot, cleanup.

Implementation steps. Extract common launch/wait/cleanup; migrate one script; then migrate the rest.

Risks/tradeoffs. A broken harness breaks many tests. Keep scripts readable and avoid hiding assertion logic.

Suggested tests. Harness self-test that launches, checks readiness, evaluates a trivial expression, and cleans up child processes.

17. Promote automation hooks into a documented Test Adapter P1 medium refactor

Problem. Test hooks are attached to window and expose internals. They are useful, but their Interface is implicit and can constrain refactors accidentally.

Evidence. renderer.js:1934-1988 exposes __nethackAutomation, __nethackPromptTest, and __nethackTooltipTest; test scripts depend on these exact names.

Recommended approach. Create a documented Test Adapter module that exposes stable test commands and read-only state snapshots. Keep private internals private.

Implementation steps. Define state snapshot shape; keep old hook names as compatibility aliases; make scripts consume the stable adapter.

Risks/tradeoffs. Too narrow a test adapter may force tests back to DOM scraping. Include both domain state and selected DOM metrics.

Suggested tests. Contract test for adapter presence, snapshot fields, prompt event injection, tooltip setup, replay start/stop.

E. Prompt/input handling and UX state

18. Model modal/focus state explicitly P1 medium refactor

Problem. Keyboard routing depends on DOM state checks, globals, and implicit priority among intro dialog, interaction dialog, direction helper, text inputs, buttons, and game grid. Focus bugs are likely as UI grows.

Evidence. renderer.js:797-864 interaction dialog setup; 941-944 document/intro key stop propagation; 1791-1932 cancel/key routing and text-edit checks.

Recommended approach. Introduce a Focus/Mode module with explicit modes: world, prompt, menu, text entry, intro, document, contextual prompt, stopped. Command Gateway asks this module whether a key should become a NetHack command.

Implementation steps. Define mode derivation from state; replace scattered dialog.open/activePrompt checks; add debug exposure of current mode.

Risks/tradeoffs. Derived mode can get stale if not centralized; use selectors over duplicated mutable state.

Suggested tests. Text input does not send commands; Escape cancels correct mode; intro space/continue behavior; active button outside direction helper is ignored; direction helper keys route correctly.

19. Replace prompt regex scatter with named domain rules P2 quick win

Problem. Regexes encode important NetHack prompt knowledge but are hard to audit. Some patterns are duplicated in tests.

Evidence. renderer.js:963-1083 prompt/menu title regexes; 1184-1191 menu kind regexes; scripts/fixture-view-test.js:44-60 duplicates a subset.

Recommended approach. Create a Prompt Rules module with named rules and examples: direction prompt, inventory action, item class, yes/no, file/name prompt, ground menu, passive ground look.

Implementation steps. Move regexes into data objects with names and comments; tests assert each rule's positive/negative examples.

Risks/tradeoffs. NetHack text can vary; rules should fail open to generic input, not block play.

Suggested tests. Table-driven prompt examples from fixtures and hand-curated negative examples.

F. Log/message handling and observability

20. Separate raw shim log from user message log P1 quick win

Problem. Raw shim event display and player-facing messages are both managed in renderer globals. They have different retention, redaction, and UI needs.

Evidence. renderer.js:80-84 shim log state; 1556-1561 exit appends raw status; 1565-1581 raw shim flush; 652-668 user message append.

Recommended approach. Build two modules: Message Log for player messages and Diagnostics Log for raw event stream. Diagnostics can keep event counts, seen names, sample payloads, parse errors, and caps.

Implementation steps. Extract flushShimEvents and raw log state; add parse-error event from main normalizer; expose diagnostics to debug panel.

Risks/tradeoffs. Extra debug structure should not slow hot event handling; batch updates remain important.

Suggested tests. Raw log cap at 400; seen names sorted; user message cap unaffected; parse-error payload displays safely.

21. Add structured app diagnostics for architectural seams P2 larger improvement

Problem. Debug panel shows useful raw output, but it does not summarize health of the main seams: process, protocol, reducer state, asset resolver, command gateway, and render performance.

Evidence. renderer.html:98-125 debug panel sections; renderer.js:177-190 automation state; renderer.js:173-174 render stats.

Recommended approach. Add a Diagnostics Snapshot module that collects state from each deep module and feeds both debug UI and automation tests.

Implementation steps. Define snapshot fields; reuse in automationState; display summarized status in debug panel.

Risks/tradeoffs. Diagnostics can become a dumping ground; keep it read-only and derived.

Suggested tests. Snapshot contains module health fields after startup, after shim start, after fixture events, and after stop.

G. Build/package and migration posture

22. Introduce a documented module map and migration checklist P2 quick win

Problem. The app has grown through focused fixes and tests, but there is no visible architecture map. Future contributors will keep adding to renderer.js because that is where every precedent lives.

Evidence. No architecture doc was found; renderer.js contains all major renderer behaviors; package scripts indicate multiple test categories but no module ownership guide.

Recommended approach. Add an Electron architecture README that names modules, seams, allowed dependencies, test surfaces, and fixture workflow. This report can be the seed.

Implementation steps. Create electron-poc/docs/architecture.md; include module map, event flow, command flow, asset flow, and testing matrix; update as extractions land.

Risks/tradeoffs. Docs can rot; make it part of code review and link test commands.

Suggested tests. Not code tests; add a lightweight docs checklist to PR template or task checklist.

Suggested implementation sequence

  1. Quick wins: document architecture map; validate preload shapes; extract prompt rules, message log, status HUD, and manifest validation.
  2. Medium refactors: asset resolver, command gateway, interaction state, test harness library, recording validator.
  3. Large improvements: game process module, shim event protocol normalizer, game state reducer, dungeon view model, replay runner.

The safest path is inside-out: first extract pure modules with fixture tests, then move DOM/process adapters. Avoid creating hypothetical seams with one adapter unless the module provides clear depth, leverage, and locality.
