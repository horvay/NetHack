Electron NetHack GUI-first input implementation plan

Purpose: Convert every normal Electron NetHack prompt/input workflow from terminal-style typed-character operation into discoverable clickable/tappable UI. Keyboard input remains fully supported as standard UI navigation: focus visible controls, activate selected/default buttons, toggle rows, and filter visible lists. Normal play should not require knowing y/n, inventory letters, selector letters, object-class symbols, vi directions, or command names.

Source list: electron-poc/typed-input-command-report.html, verified against the current Electron prompt surfaces, fixtures, and shared/shim modules cited there.

Non-goal for this document: no production implementation yet. This is a concrete implementation plan and test plan.

Recommended architecture

1. Typed answer adapter

Keep NetHack/shim as the source of truth. Every GUI control submits the same answer the shim expects: one character for yn_function, selector strings for select_menu, line text for getlin, direction key or map coordinate for poskey, and command names for get_ext_cmd.

2. Prompt classification layer

Extend prompt-rules.js/interaction-model.js into a typed prompt descriptor: confirmation, inventoryAction, menuPickOne, menuPickAny, quantity, directionTarget, objectClass, commandPalette, freeText, readOnly, dangerousConfirm.

3. Reusable renderer components

Add component-style renderer functions in renderer.js or split modules later: choice bar, inventory picker, menu picker, quantity stepper, compass/target overlay, object-class grid, command palette, text dialog, document window, context action sheet.

4. Accessibility-first modals

All prompt UI must have visible labels, focus trap, ARIA roles, clear default/cancel buttons, screen-reader announcement of prompt text, and standard keyboard navigation. Focus is always on a visible UI control; keyboard events operate that control, then the adapter maps the control choice to the hidden NetHack selector answer. ESC maps to visible Cancel/No/Back only when that action is safe and available.

Keyboard navigation and focus policy

  • Keyboard selects visible UI, not hidden NetHack letters: every keyboard path moves focus/selection among rendered controls and then submits the selected control's internal data-answer. The UI may show raw selector letters as secondary/debug hints, but users should not need to know them.
  • Default button policy: Enter activates the selected control, or the visible default button when focus is in a neutral text/list context. Safe/default actions are commonly “Yes” only for low-risk continuation prompts. Destructive, irreversible, or dangerous prompts must default focus to the safe action and must never confirm the dangerous action through an accidental Enter.
  • Cancel/back policy: Escape maps to a visible Cancel, No, Close, or Back action where appropriate. It never maps to an affirmative destructive action; if NetHack has no safe cancel for the current prompt, the UI must say so and require an explicit visible choice.
  • Lists and menus: Arrow Up/Arrow Down move the active row in vertical option lists; Arrow Left/Arrow Right move across horizontal choices, tabs, compass rows, and quantity steppers. Space toggles checkboxes and multi-select rows. Tab/Shift+Tab traverse focusable controls in DOM order.
  • Search/typeahead: typing in a search field or list typeahead filters or jumps among visible labels. Typeahead is for discoverability and speed only; it must not require memorizing inventory selector letters, object-class symbols, vi keys, or command names.
  • Small fixed-option prompt rule: prompts/modals with roughly 2–4 fixed visible options (yes/no/confirm, small class/special selectors, tiny action sets, and small PICK_ONE/PICK_ANY menus) must not show a search/filter/type field. They show only clear visible choices plus appropriate Cancel/Confirm controls. Free-text prompts keep text fields, and larger dynamic lists/inventory/catalogs keep filtering.
  • Accessibility/focus management: modals use focus traps, initial focus is deterministic and safe, focus returns to the initiating control after completion, active-descendant state is announced for listboxes/grids, and every control has an accessible name describing the visible action and consequences.
  • Input routing isolation: when any modal, picker, menu, prompt panel, command palette, text field, context sheet, target overlay, or UI selection model is active, keyboard events used for UI navigation must be captured by that UI layer and must not also be forwarded to the map/game command gateway. For example, Arrow Up/Arrow Down moving selection in a modal/list must not move the player, scroll the map command layer, attack, travel, or interact with map cells.
  • Prompt interaction boundary: Enter, Escape, Space, Tab/Shift+Tab, arrows, Home/End, PageUp/PageDown, and typeahead keystrokes inside active UI are handled/stop-propagated by the focused component or routed only through the prompt interaction model. They reach the NetHack/shim adapter only as the selected prompt answer, never as simultaneous global commands.
  • Text fields versus global shortcuts: text inputs own printable characters, editing keys, IME composition, arrows, Home/End, and selection shortcuts while focused. Global shortcuts remain available only when explicitly allowed, non-conflicting, and outside editable fields; emergency shortcuts must be documented and must not submit hidden prompt answers accidentally.

Cross-cutting implementation rules

  • Never remove keyboard support: keep raw NetHack keys/selectors as advanced fallback, but visually de-emphasize them.
  • Keyboard means standard UI navigation: Tab/Shift+Tab moves focus; arrows move active options; Enter activates selected/default visible controls; Space toggles checkboxes/multi-select rows; Escape maps to visible Cancel/No/Back where safe. While such UI is active, these events are consumed by that UI layer and must not fall through to map movement, combat, travel, pickup, or the global command gateway.
  • Hide selector letters behind controls: renderer controls map internally to NetHack/shim answers via data-answer, menu serializers, direction descriptors, and command gateway calls. Normal UI copy should never instruct players to type raw selector letters.
  • Do not infer irreversible actions silently: destructive/unsafe prompts require explicit labelled UI, safe initial focus, and no dangerous default activation by accidental Enter or Escape.
  • Prefer structured state over text scraping: short term can parse prompts/menus; long term shim should expose item/equipment/spell/option metadata.
  • Every GUI component must serialize to a tested NetHack answer: unit-test serializers for choices, menu selections, counts, ranges, class symbols, directions, and command names.
  • Fallback for unknown prompts: render a generic labelled choice/text/menu component with raw keyboard hints, and log classification gaps for fixture capture.
  • Single active input owner: maintain an explicit input-routing state: map/game command gateway is active only when no modal/picker/menu/prompt/text field/context sheet/selection model owns focus. Active UI owners call preventDefault/stopPropagation or equivalent dispatcher handling for navigation keys, and submit to NetHack only through the typed-answer adapter.
  • Focus trap requirement: modal and prompt panels trap focus until resolved/cancelled, restore focus on close, and prevent background map cells or toolbar controls from becoming keyboard-active underneath the prompt.
